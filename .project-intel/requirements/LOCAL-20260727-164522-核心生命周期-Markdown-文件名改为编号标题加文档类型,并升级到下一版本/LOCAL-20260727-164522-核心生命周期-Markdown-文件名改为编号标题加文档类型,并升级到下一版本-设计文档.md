# LOCAL-20260727-164522_核心生命周期 Markdown 文件名改为编号标题加文档类型，并升级到下一版本_设计文档

## 需求问题概述

LOCAL-20260727-164522 要求生命周期 Markdown 产物同时满足文件名可读和内容结构标准化。现有代码已通过 `src/requirements/artifacts.ts` 处理可读文件名，通过 `src/requirements/state-machine.ts` 生成文档内容，通过 `src/requirements/documents.ts` 统一校验登记文档。本次设计需要在不破坏历史档案的前提下，升级新生成文档的内容结构。

## 需求描述

需求目标是将新生成的四类核心生命周期文档对齐样例目录标准：需求文档对齐 PRD，设计文档对齐样例 `plan/index.md`，测试文档对齐样例 `test.md`，收口文档对齐样例 `收口档案.md`。复盘文档不作为独立生命周期类型新增，相关归纳沉淀进入收口档案。

## 需求提出部门及联系人

提出方为本仓库维护者，联系人为当前本地项目负责人。该需求来源于用户对生成档案命名和内容标准的连续反馈。

## 电信需求负责人

不涉及电信侧接口或生产系统负责人。当前执行负责人为本仓库发布执行人。

## 需求适用范围

适用于 Project Intelligence 本地 CLI 的 requirement 级产物生成、登记校验和发布校验。影响路径包括 `src/requirements/state-machine.ts`、`src/requirements/documents.ts` 以及相关测试文件。

## 需求期望完成时间

本次发布窗口内完成，目标版本为当前 `package.json` 中的 0.7.3。

## 设计相关选项

1. 文档文件名继续由 artifactFilename 统一生成，避免在状态机里重复拼接命名规则。
2. 文档内容模板集中在 generatedArtifactText，保持生成入口单一。
3. 校验层在 `src/requirements/documents.ts` 同时接受新版章节和旧版章节，满足 AC-03 的历史兼容。
4. 测试优先覆盖生成内容的章节结构、收口档案格式和旧文档兼容登记。

## 场景分析

场景一：用户生成新需求文档。系统从 manifest 读取需求号、标题、单据类型和验收标准，生成包含背景目标、范围、角色、流程、功能、规则、数据口径、验收标准和待确认项的 PRD 风格文档。

场景二：用户生成设计文档。系统生成包含目录、概述、架构设计、核心模块、技术决策、已知限制、扩展方向和相关资源的设计文档，并保留源码依据。

场景三：用户生成测试文档。系统生成包含测试环境、核心规则、功能用例、边界异常、自动化回归建议、测试清单和代码索引的测试文档。

场景四：用户生成收口文档。系统生成带 YAML frontmatter 的收口档案，聚合需求 ID、目录、状态、git_range、历时、产物清单、测试汇总、知识命中、澄清缺口和沉淀候选。

场景五：历史文档登记。历史 `requirement.md`、`design.md`、`test-report.md`、`closure-summary.md` 或旧章节文档仍应通过读取和登记，不因新模板上线中断。

## 风险考虑

1. generatedArtifactText 是所有 lifecycle artifact 的共享生成入口，变更风险较高，需要用 GitNexus impact 和回归测试确认影响范围。
2. validateRequirement 和 validateDesign 若只接受新版结构，会破坏历史任务；必须保留旧版兼容。
3. 测试文档当前不是 finish 门禁的严格文档校验入口，新增模板不能让无执行证据的测试计划误判为完成证据。
4. 收口档案中 git_range 和测试汇总依赖 manifest 中已有证据，缺失时必须诚实输出 `未记录` 或 `cannot_verify`。

## 实现方案

1. 在 `src/requirements/state-machine.ts` 中升级 requirement、design、test、closure 四类生成内容。
2. 保留 `src/requirements/artifacts.ts` 的命名规则，不重复修改文件名逻辑。
3. 在 `src/requirements/documents.ts` 中同时识别旧版“文档信息/背景与现状”结构和新版“业务需求文档/背景与目标”结构。
4. 在 `src/requirements/documents.ts` 中同时识别旧版 CRM 设计结构和新版样例设计结构。
5. 在 `src/__tests__/review-finish-graph.test.ts`、`src/__tests__/state-machine.test.ts` 或相邻测试中补充断言，覆盖生成文档标准章节。
6. 发布前执行单元测试、构建、release 校验、Project Intelligence check 和 GitNexus detect_changes。
