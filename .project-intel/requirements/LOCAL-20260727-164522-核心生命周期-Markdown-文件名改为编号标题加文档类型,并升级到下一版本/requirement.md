# LOCAL-20260727-164522 核心生命周期 Markdown 文件名改为编号标题加文档类型，并升级到下一版本 需求文档

## 文档信息

- 需求号：LOCAL-20260727-164522
- 需求名称：核心生命周期 Markdown 文件名改为编号标题加文档类型，并升级到下一版本
- 单据类型：Requirement

## 背景与现状

当前需求、Bug 生命周期文档已经从固定文件名逐步迁移到“编号 + 标题 + 文档类型”的可读命名，便于用户在文件系统、GitHub 和发布包中直接识别档案内容。上一轮已处理核心文件名和版本发布问题，但用户补充要求：文档内部结构也要参考样例目录 `2026-07-14-新增活动页面预填模板预览与用户指引优化/` 下的标准。

样例目录包含 PRD、设计、测试、复盘和收口档案五类资产。当前生命周期稳定产物仍是需求、设计、测试、收口四类，因此本次将 PRD 对齐到需求文档，设计对齐到设计文档，测试对齐到测试文档，收口档案对齐到收口文档；复盘信息作为收口归纳能力的一部分，不新增第五个生命周期产物。

## 目标

1. 新建需求或 Bug 生命周期产物时，核心 Markdown 文件名继续使用编号、标题和文档类型组成的可读名称。
2. 新生成的需求、设计、测试、收口文档在内容章节上对齐用户提供的样例目录标准。
3. 历史固定文件名和旧版内容结构仍可登记、读取和校验，避免破坏既有档案。
4. 本次变更随 0.7.3 版本发布，npm 包和 GitHub tag 均可被用户拉取验证。

## 业务场景

1. 用户新建需求，系统生成 `需求号-标题-需求文档.md`，内容具备 PRD 风格的背景、范围、角色、流程、功能、规则、验收和待确认项。
2. 用户新建 Bug，系统生成 `Bug号-标题-Bug文档.md`，并继续沿用现有 Bug 文档能力。
3. 用户生成设计、测试、收口文档，文件名分别包含 `设计文档`、`测试文档`、`收口文档`，内容结构可直接按样例目录阅读和交付。
4. 历史任务仍引用 `requirement.md`、`design.md`、`test-report.md`、`closure-summary.md` 时，系统不能因文件名或旧章节不同而拒绝登记。

## 范围

本次包含：

1. 调整生命周期产物生成模板，覆盖 requirement、design、test、closure 四类核心文档。
2. 调整文档校验逻辑，使新版章节可通过校验，并保留旧版章节兼容。
3. 补充自动化测试，证明新生成模板包含样例目录标准章节。
4. 维持既有发布校验、构建和 package 版本一致性。

本次不包含：

1. 不新增第五类 retrospective 生命周期产物。
2. 不删除历史 Python 迁移遗留以外的用户文件。
3. 不调整 GitNexus、Understand-Anything 或外部发布平台的认证流程。

## 非目标

1. 不强制迁移已经归档的历史需求目录和历史 Markdown 文件名。
2. 不把样例目录本身作为发布包内容提交。
3. 不改变生命周期状态机的核心状态流转语义。

## 业务规则与异常边界

1. 文档文件名由需求号或 Bug 号、标题和文档类型组成，标题继续沿用现有目录名清洗规则，避免路径非法字符。
2. 需求文档内容以 PRD 风格为主，但验收标准必须与 manifest 中的 `acceptanceCriteria` 保持同 ID、同语义。
3. 设计文档必须保留源码依据和技术决策，不能只生成泛化说明。
4. 测试文档可以先作为计划生成，但只有记录实际命令、结果和 AC 映射后才能作为完成证据。
5. 收口文档需要包含 YAML frontmatter、历时、产物清单、测试汇总、知识命中、澄清缺口和新确认沉淀候选。
6. 旧文件名和旧章节结构仍可登记，兼容能力不随新模板发布移除。

## 验收标准

- AC-01：新建需求/Bug 的核心 Markdown 文件名使用编号-标题-文档类型.md
- AC-02：requirement 文档按单据类型区分为需求文档或Bug文档，设计/测试/收口使用设计文档/测试文档/收口文档
- AC-03：旧 requirement.md/design.md/test-report.md/closure-summary.md 仍可读取和登记，不破坏历史档案
- AC-04：package、运行时版本和插件 manifest 升级到下一 patch 版本并保持发布校验通过
- AC-05：新生成的需求、设计、测试、收口文档内容结构对齐样例目录中的 PRD、设计、测试和收口档案标准
