# 需求/问题概述

## 需求描述

Project Intelligence 已具备需求文档、设计文档、测试文档和收口文档的 canonical 文件及部分门禁，但 Intake 与 Skills 仍允许对必选文档选择 `later`，导致流程描述与机器行为不一致。本次将四类文档统一为不可延期的生命周期产物：有现成文件时登记到规范目录，没有时选择生成；用户只提供设计文档时，由 Project Spec 先读取设计事实，提炼业务 spec 和验收标准，再登记设计文档。测试执行与 finish 分别负责持续生成测试文档和自动生成收口文档。

# 场景分析

## 场景分析

### 场景一：自然语言需求自动补齐四类文档

- 场景名称：没有现成文档的新需求交付
- 参与对象：需求提出人、Project Intelligence Agent、CLI 状态机
- 前置条件：用户提供需求身份、版本日期和外部接口影响，没有提供现成 spec 或设计文档
- 处理过程：Intake 默认把需求文档和设计文档选择为生成；Project Spec 形成业务 spec 与 AC，Project Design 形成源码佐证设计；实施阶段真实测试生成测试文档，评审通过后 finish 自动生成收口文档
- 目标结果：同一日期化需求目录内稳定存在四个标题化 Markdown 文件，manifest 记录各产物摘要和生命周期状态
- 异常边界：任一文档未完成、校验失败、哈希失效或被篡改时，状态机拒绝进入对应下游状态

### 场景二：仅提供设计文档时反向生成 spec

- 场景名称：设计先行、缺少独立业务 spec
- 参与对象：需求提出人、Project Intake、Project Spec、Project Design
- 前置条件：用户提供仓库内设计文档路径，但没有单独的需求/Bug 文档
- 处理过程：Intake 保存设计登记路径并把 requirement 动作设为生成；Project Spec 在设计登记前读取该路径，以设计中的目标、场景、规则、异常和影响范围为事实来源，生成 canonical spec 和一致 AC；随后 Project Design 校验并登记原设计
- 目标结果：设计信息无需用户重复录入，spec 仍先于 ready 完成，且来源关系在工作流说明和文档内容中可追溯
- 异常边界：设计路径越出仓库、不存在、内容与需求身份矛盾或无法形成可测试 AC 时停止流程，不生成猜测性 spec

### 场景三：已有文档登记与历史档案兼容

- 场景名称：复用已有 spec、设计或测试报告
- 参与对象：开发人员、Project Intelligence CLI、历史需求档案
- 前置条件：仓库中已有可验证文档或结构化测试报告
- 处理过程：CLI 验证源文件和路径，将内容复制或汇总为规范目录下的 canonical 标题化文档；旧短文件名和旧目录只作为读取兼容，不改变新需求规则
- 目标结果：避免重复编写已有内容，同时保证新归档仍具备统一的四文档结构
- 异常边界：register 路径与 Intake 确认路径不一致、报告无真实测试计数或旧文件无法归属需求时明确拒绝，不静默猜测

## 风险考虑

主要风险是共享状态机行为收紧后，依赖 `later` 的旧脚本会收到错误；通过保留历史 manifest 读取和清晰报错降低迁移成本。另一个风险是 Skill 文案与 CLI 规则漂移；通过 Skill 契约测试和三端安装规则文本断言保持一致。

紧急方案：

若新门禁导致异常，可回退本次 Git 提交；历史档案数据不迁移、不删除，因此回退不需要数据恢复。

# 实现方案

### Intake 与文档动作状态机

- 改造目的：保证新需求从创建时就具有明确且不可延期的 spec、设计文档处理策略
- 当前与目标：当前未提供动作时 manifest 可没有选择，显式 `later` 可写入；目标是缺省使用 `generate`，仅允许 `generate` 或 `register`
- 处理规则：存在 requirement/design 路径时只允许配套 register；未提供路径时默认 generate；四类必选文档的 defer 请求统一失败，实施计划不受影响
- 字段流转：Intake 参数 → `workflowSelections.requirement/design` → spec/design Skills → canonical artifact
- 调用顺序：CLI Intake 调用状态机创建 manifest，后续 Project Spec 与 Project Design 按选择生成或登记
- 异常与兼容：历史 `later` 值保持可读取但无法通过现有 readiness；已有 register 路径规则与旧目录解析保持不变
- 源码依据：`src/commands/orchestration.ts#runIntake`
- 源码依据：`src/requirements/state-machine.ts#createRequirement`
- 源码依据：`src/requirements/state-machine.ts`

### 设计文档回退生成 spec

- 改造目的：用户只提供技术设计时仍自动满足公司的 spec 交付要求
- 当前与目标：当前 Project Spec 固定要求先有独立需求输入；目标是允许读取 Intake 已保存的 design path，把设计事实转成 canonical 需求/Bug 文档和 manifest AC
- 处理规则：有独立 spec 时优先使用；无 spec 且有设计时从设计提炼背景、目标、范围、场景、业务规则、异常边界和可观察 AC；设计与需求身份冲突时停止
- 字段流转：`workflowSelections.design.path` → Project Spec 内容分析 → requirement artifact 与 acceptanceCriteria → Project Design 登记
- 调用顺序：Project Intake 保存选择，Project Spec 读取设计源并生成 spec，文档校验器验证身份和 AC，Project Design 再登记设计
- 异常与兼容：不创建第二套 specs 目录，不把设计的实现细节机械复制为业务规则；旧的 spec-first 路径保持不变
- 源码依据：`src/requirements/documents.ts#validateDeliveryDocumentInRepository`
- 源码依据：`src/requirements/state-machine.ts`

### 测试文档、收口文档与完成门禁

- 改造目的：让后半程产物同样不可延期，并保持真实证据约束
- 当前与目标：当前测试契约和 Skills 仍暴露 `later`，收口 Skill 会询问动作；目标是测试仅允许 generate/register，finish 缺收口时直接自动生成
- 处理规则：测试命令记录真实执行计数和 AC 映射后维护标题化测试文档；finish 校验测试、review 和文件范围后生成收口文档，再执行完成门禁
- 字段流转：测试契约与命令结果 → testEvidence/test artifact → review → closure artifact → finishResult
- 调用顺序：test-contract、begin、test、review、finish、maintain
- 异常与兼容：无真实测试计数、证据过期、文档哈希失效或已有无效收口文件时拒绝完成；register 结构化测试报告继续支持
- 源码依据：`src/requirements/state-machine.ts#setTestContract`
- 源码依据：`src/commands/test.ts#runTest`
- 源码依据：`src/commands/finish.ts#runFinish`

### Agent Skills 与三端适配规则

- 改造目的：保证 Codex、Claude Code 和 ZCode 不再给出可绕过必选文档的提示
- 当前与目标：当前相关 Skills 仍询问 generate/register/later；目标是只判断“已有则登记、缺失则生成”，并明确设计回退 spec
- 处理规则：同步 Intake、Spec、Design、Test、Finish、Task Skills 和安装规则；Skill 契约校验必须检查强制语句并禁止必选文档 defer 语句
- 字段流转：插件 Skills 与 managed agent rules → 各宿主 Agent 的运行指令 → CLI 命令
- 调用顺序：install/init 生成适配规则，Agent 依序调用生命周期 Skills 和 CLI
- 异常与兼容：不改变宿主命令名称或插件清单，不修改安全与外部路径策略
- 源码依据：`src/commands/agent-rules.ts#codexAdapterRules`
- 源码依据：`scripts/validate-skill-evals.mjs`
