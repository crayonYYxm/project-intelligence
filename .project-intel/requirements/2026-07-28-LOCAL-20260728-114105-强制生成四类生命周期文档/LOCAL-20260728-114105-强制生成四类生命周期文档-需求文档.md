# 业务需求文档: 强制生成四类生命周期文档
> feature-id: LOCAL-20260728-114105
> 状态: 草稿
> 日期: 2026-07-28
> 业务ID: LOCAL-20260728-114105

## 1. 背景与目标

公司交付规范要求每个正式需求或 Bug 都留存一套可追溯的 spec（需求/Bug 文档）、设计文档、测试文档和收口文档。当前 Project Intelligence 的状态机虽然会在 ready、test 和 finish 阶段校验部分产物，但 Intake、Skills 与帮助文档仍允许把必选文档选择为 `later`，收口 Skill 也会再次询问是否生成，造成“文档宣称必选、流程仍可延期”的不一致。

本需求将四类文档固化为生命周期强制产物：有现成文档时登记并复制到规范目录，没有现成文档时自动选择生成；如果用户只提供设计文档而没有独立 spec，Project Spec 必须先从设计内容提炼业务目标、范围、规则和验收标准，形成规范 spec 后再进入设计登记。最终同一需求目录必须具备四个标题化 Markdown 文件及可验证的 manifest 记录。

## 2. 需求范围

### 2.1 本次包含

- 调整新需求 Intake 的默认文档选择，未提供动作时对需求文档和设计文档使用 `generate`。
- 禁止需求文档、设计文档、测试文档和收口文档使用 `later` 或 `defer` 绕过生命周期。
- 支持仅提供设计文档的输入方式：Project Spec 读取该设计文档并先生成 spec 与同编号验收标准。
- 保留已有 spec、设计或测试报告的 `register` 能力，登记后仍在规范目录形成标题化四类文档。
- 固化测试文档在需求级测试执行后生成、收口文档在 finish 阶段自动生成的行为。
- 同步 Codex、Claude、ZCode 适配规则、相关 Skills、README 和使用指南。
- 增加状态机、CLI、Skill 契约及完整生命周期回归测试。

### 2.2 本次不包含

- 不改变实施计划的可选属性。
- 不删除历史短文件名、旧需求目录或 `by-id` 档案的读取兼容。
- 不修改业务项目的代码，也不新增或修改对外 API。
- 不自动发布 npm 包；本需求只提交并推送 Git。

## 3. 用户角色与使用场景

- 需求提出人：可能提供完整 spec、仅提供设计文档，或只给出自然语言需求。
- 开发 Agent：必须补齐四类文档，不能以“稍后处理”跳过公司必选产物。
- 开发与测试人员：通过同一需求目录读取设计、测试证据和收口结论。
- 评审与审计人员：通过 manifest 的产物摘要、哈希、测试证据和状态记录追溯交付过程。

核心场景包括：自然语言需求自动生成 spec 与设计；已有 spec/设计直接登记；仅有设计文档时反向生成 spec；执行测试后生成测试文档；评审通过后 finish 自动生成收口文档。

## 4. 业务流程

1. Intake 收集需求身份、用户提供的版本日期和外部接口影响，自动判断已有文档是登记还是生成。
2. Project Spec 优先处理 spec；若没有独立 spec 但存在设计文档，则以设计文档为事实来源提炼 spec 和验收标准。
3. Project Design 生成或登记设计文档，ready 门禁同时校验当前有效的 spec、设计文档和测试契约。
4. Project Task 开始实现，Project Test 运行真实测试并持续生成标题化测试文档。
5. Project Review 对当前 Git 变更和测试证据完成评审。
6. Project Finish 自动生成标题化收口文档并校验四类产物，Project Maintain 再次验证新鲜度后关闭需求。

## 5. 功能需求

1. 新建 manifest 时必须为需求文档和设计文档写入明确的 `generate` 或 `register` 选择，不能留下空选择或 `later`。
2. CLI 对四类必选文档的 `later`/`defer` 请求必须返回可理解的错误，且不能写入未解决 blocker。
3. 当 Intake 选择 `design=register` 且没有独立 requirement/spec 路径时，Project Spec 必须读取该设计源文件生成 canonical spec，不得要求用户重复提供同一信息。
4. spec 的验收标准必须与 `manifest.acceptanceCriteria` 编号和描述完全一致，生成后通过现有文档校验器并登记。
5. 测试契约只允许 `generate` 或 `register`。两种模式都必须在执行需求级测试后维护同目录的标题化测试文档。
6. finish 不再询问是否生成收口文档；缺失时自动生成，存在无效文件时明确报错，不静默覆盖用户内容。
7. ready、finish、maintain 必须继续校验产物哈希、文档结构、测试证据和当前 Git 快照。

## 6. 业务规则

- 四类必选产物定义为：需求/Bug 文档、设计文档、测试文档、收口文档。
- “spec”在本项目中对应标题化的需求文档或 Bug 文档，不新增第二套 `.project-intel/specs/` 目录。
- 有现成文档时允许登记；“强制生成”指规范目录始终形成 canonical 文档，而不是强制丢弃已有内容重写。
- 仅有设计文档时生成的 spec 必须引用设计事实，明确说明其来源，并补齐可测试的 AC。
- 设计文档不得承载验收标准章节；AC 只保存在 spec 与 manifest。
- 四类必选产物不可延期，实施计划仍只在 complex 需求或用户明确要求时生成。
- 不允许用 lint、构建或空命令冒充测试文档中的行为验证证据。

## 7. 数据口径与状态说明

- `workflowSelections.requirement/design.action` 仅允许 `generate` 或 `register`。
- `testContract.reportAction` 仅允许 `generate` 或 `register`。
- 新需求状态仍按 `draft -> specified -> designed -> ready -> implementing -> verified -> reviewed -> finished -> closed` 流转。
- `specified` 表示 spec 已验证登记，`designed` 表示设计文档已验证登记。
- `verified` 前必须存在当前 Git 快照对应的有效测试证据和标题化测试文档。
- `finished` 前必须存在有效收口文档；`closed` 前再次校验四类文档及 finish 新鲜度。
- 历史 manifest 中已有的 `later` 记录继续可读取，但不能通过 ready/finish，也不能在新流程中新增。

## 9. 权限与可见性

沿用现有本地仓库权限。生成或登记的文档只写入当前仓库 `.project-intel/requirements/<YYYY-MM-DD>-<id>-<title>/`，不访问仓库外路径，不改变 GitHub、npm 或业务系统权限模型。

## 10. 异常与边界场景

- 设计源文件不存在、越出仓库或内容无法验证时，spec 回退流程必须失败并指出路径或验证原因。
- canonical spec 已存在且包含内容时，不得隐式覆盖；应继续完善并登记，显式 `--replace` 仍需用户授权。
- 用户同时提供 spec 和设计文档时，优先使用并验证 spec，不做反向生成。
- 历史需求含 `later` 或旧短文件名时允许查询和迁移，但不能用旧 `later` 绕过新门禁。
- 测试未执行、报告无真实测试计数、验收标准未覆盖或证据过期时，不得 finish。
- 收口文件已存在但未有效登记时，不自动覆盖，提示先登记或显式处理。

## 11. 验收标准

- AC-01：新需求未显式选择文档动作时默认生成需求文档和设计文档，四类必选文档均不允许 later 或 defer。
- AC-02：仅提供设计文档且没有独立 spec 时，project-spec 必须先依据该设计文档生成并登记同目录的标题化需求或 Bug 文档及一致的验收标准。
- AC-03：测试契约只允许 generate 或 register，执行需求级测试后必须生成同目录的标题化测试文档并登记当前证据。
- AC-04：finish 必须自动生成并登记同目录的标题化收口文档，四类文档缺失、失效或被篡改时不得完成或关闭需求。
- AC-05：Codex、Claude 与 ZCode 的安装规则及相关 Skills 必须采用一致的四文档强制流程，不再询问是否 defer 必选文档。
- AC-06：已有文档 register 路径以及历史短文件名和旧需求目录继续可读取，实施计划仍保持可选。
- AC-07：新增行为具备 RED、GREEN 和完整回归证据，构建、项目检查及发布检查全部通过。
