## 概述 / Overview

为需求生命周期增加显式版本日期。Intake 接收用户给出的版本日期，规范化后写入 requirement manifest；新档案目录以版本日期开头，后续所有生命周期命令通过 manifest 身份解析同一目录。既有目录布局继续只读兼容，不做自动迁移。

## 架构设计 / Architecture

### 整体结构

入口层在 `runIntake` 和 `runRequirement create` 读取 `--version-date`，领域层统一调用日期规范化函数，状态机将 `versionDate` 持久化到 manifest。目录层分别维护“目录名”和“文档文件名前缀”：目录名包含日期，文档名不包含日期。作用域层同时识别新旧目录。

### 数据流

用户版本（如 `7.23版本`）→ CLI `--version-date` → 日期规范化与真实日历校验 → manifest `versionDate=2026-07-23` → `2026-07-23-CRM-req76637-标题/`。后续文档生成读取已存在目录及 manifest，不重新计算日期。

## 核心模块 / Core Modules

- `src/commands/orchestration.ts#runIntake`：校验实施型 intake 已提供版本日期并传入状态机。
- `src/commands/requirement.ts#runRequirement`：为底层 requirement create 暴露相同参数。
- `src/requirements/artifacts.ts`：新增日期规范化函数，接受完整日期和省略年份的中文/点号形式，输出标准日期。
- `src/requirements/artifacts.ts#requirementDirectoryName`：在 240 字节上限内生成日期、编号、标题目录。
- `src/requirements/state-machine.ts#directManifestPaths`：按 manifest 中的需求号识别日期前缀和旧布局。
- `src/requirements/scope.ts#isUnderRequirementDir`：从证据范围中过滤当前需求的新旧档案目录。
- `skills/project-intake/SKILL.md`：要求 Agent 在实施型任务中收集并传递版本日期。

## 技术决策 / Key Decisions

- 版本日期为用户输入的业务属性，禁止静默使用创建时间。
- 未写年份时使用命令执行时的当前年份，规范化结果立即持久化，避免跨年或跨日漂移。
- `requirementDirectoryName` 与文档文件名前缀解耦，保证目录增加日期后 Markdown 文件名规则不变。
- 目录解析以 manifest `requirementId` 为身份依据，不仅依赖目录字符串前缀，以兼容新旧布局并可靠发现重复档案。
- 已有 manifest 缺少 `versionDate` 时保持可读，不强制补写或移动目录。

## 已知限制 / Known Limits

| 限制 | 影响范围 | 应对措施 |
|------|----------|----------|
| 省略年份的日期依赖执行当年 | 跨年录入历史版本 | 历史版本使用完整 `YYYY-MM-DD` |
| 旧目录不自动增加日期 | 已有档案的视觉一致性 | 保持兼容；如需迁移另立需求 |

## 扩展方向 / Extension Points

后续可在不改变当前 manifest 字段的前提下，为版本日期增加交互式提示或从正式需求文档元数据中提取候选值；自动提取仍需用户确认后才能创建档案。
